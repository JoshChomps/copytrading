# Code review: 2026-07-25 (max-effort, multi-agent)

Durable record of a full review of branch `fix/local-rebuild-and-timescale`
(11 commits + the then-uncommitted `rank/features.py`). Every finding below was
**verified by executing code against the live 41,415-trade database**, not by
reading alone; measured numbers are quoted so the fixes can be checked against
them.

Keep this file. It is the only record of *why* several constants and guards
look the way they do, and of which reported numbers were wrong before the fix.

**Status legend:** ✅ fixed · ⬜ open · 🚫 won't fix (with reason)

---

## Why this review mattered

Three of the findings invalidated numbers that had already been reported as
results. That is the recurring failure mode in this project: an analysis runs
clean, produces a plausible table, and the table is wrong for a reason no test
covers. The corrections are recorded in §Corrections at the bottom.

## Tier 1: findings that changed reported results

### 1. ✅ `engine.py`: price guard rejected trades using FUTURE data
**Was:** `seg = ffill_vals[pos : end + 1, ci]; if np.nanmin(seg) <= 0: unpriceable += 1; continue`
where `end = min(pos + max_h, len(cal) - 1)` and `max_h = max(horizons)`.

A trade's inclusion **at the 1-day horizon** depended on prices up to 504 days
later, because `timescale` passes the whole horizon grid. Reproduced: the same
trade with `horizons=[1]` is kept (`unpriceable=0`) and with `horizons=[1,504]`
is dropped (`unpriceable=1`).

Every cell of the sweep, including the entire SHORT band that produced the
project's headline result: was conditioned on the name still printing a valid
price two years later. It also made the sweep's h63 sample differ from the h63
sample every other command computes, and inflated the `unpriceable` counter
that `report.py` publishes as a "survivorship caveat".

**Fix:** a non-positive price is treated as **end of data** (like a delisting),
truncating the usable path, instead of rejecting the whole trade. Short
horizons keep the trade; only horizons that would have to read through the bad
print return NaN. The entry-price guard (`p0 <= 0`) is unchanged and still
rejects outright, which is correct, there is no return without an entry price.

### 2. ✅ `cli.py timescale`: "large ($ top quartile)" selected 98.5% of trades
**Was:** `big = pt["amount"] >= pt["amount"].quantile(0.75)`

Congress amounts are **bucket midpoints**, not real sizes: 9,396 of 12,750
priced buys share the single value `8000.5` (the $1,001-$15,000 bucket).
Therefore `quantile(0.10) == quantile(0.75) == 8000.5`, and `>=` sweeps the
entire mode in: selecting **12,563 / 12,750 = 98.5%**.

The grid printed `large ($ top quartile) h=1 → mean −0.272%, t −7.05`, which is
`ALL buys h=1 → −0.280%, t −7.17` relabelled. Large trades were never isolated.
The six near-duplicate cells also inflated the BH family from ~33 to 44 tests,
over-correcting the genuine cells, and **6 of the 20 reported FDR survivors
were these duplicates**.

**Fix:** strict `>` (which correctly yields ~26% on this data), plus an explicit
degeneracy check that reports the fraction actually selected and warns when the
quantile lands on the mode. Ranges are a known property of this dataset
(`amount_for_basis` already documents it) so the guard is permanent, not a
one-off.

### 3. ✅ `cli.py timescale`: "abnormal" subset defined with full-sample look-ahead
**Was:** `abnormal_ids = abnormal_size_ids(buys, 2.0)`

`rank/insiders.abnormal_size_ids` computes `med = g["amount_mid"].median()` over
each filer's **entire history**, so a 2016 trade was labelled "abnormal" using
2017-2026 trades.

Measured: the full-sample rule selects 1,965 trade_ids; a strictly-backward rule
(median of the filer's prior buys only, ≥3 history) selects 1,662, overlapping
on 1,601: so **364 trades (18.5% of the tested subset) were in it only because
of information that did not exist at execution time.**

This broke methodology rule 2.1, the project's first methodology invariant, even though
the *execution* remained point-in-time. Subset **definitions** are part of the
strategy and must obey the same rule.

**Fix:** new `abnormal_size_ids_pit()` using an expanding median over strictly
prior buys, with a `min_history` floor. The old function is retained for the
insider analyses that legitimately do full-sample attribution, but is now
documented as non-point-in-time.

### 4. ✅ `exits.py`: fixed-horizon baseline silently used short holds
**Was:** `last = min(last, int(max_h))`, closes at the last non-NaN bar.

`run_event_study` writes `h63 = NaN` when `pos + 63` runs past the calendar, but
`apply_exit` closed at the last valid bar and returned a real number instead.

Measured: 55 trades entered 2026-05-01 → 2026-07-20 were held **3-56 days** and
have mean net excess **+4.91%** against −0.35% for the rest. `exits` printed
`fixed 63d (baseline) n=12750 mean=−0.33%` while engine `h63`, `timescale` and
`greeks` all report `n=12695 mean=−0.3509%`; restricting to `held_days == 63`
reproduces −0.3509% exactly.

**Fix:** `apply_exit` takes `require_full` (default True for the baseline) and
returns NaN when the horizon has not elapsed, matching the engine exactly.
`vs_base` was already unbiased because both legs truncated identically, so the
"no rule beats the baseline" conclusion stands, but the baseline's own `mean`,
`hit` and `t_own` were wrong.

### 5. ✅ `leverage.py`: `maintenance=0.25` is the US Reg-T floor, not IBKR Canada
The modelled broker is IBKR **Canada** (CIRO), where standard margin on a listed
equity ≥$2.00 runs 30% (reduced-margin list) to 50%, and house minimums often
exceed 25%. The docstring even admitted "typically 25-30%" while defaulting to
the bottom of its own range.

Measured on real SPY 2015-01→2026-07 (4,000 bootstrap paths), **P(margin call)
at 2×**:

| maintenance | 25% | 30% | 35% | 50% |
|---|---|---|---|---|
| P(call) at 2× | 11.6% | **17.0%** | 25.3% | 96.1% |

`max_safe_leverage` drops 1.50× → 1.25× at 50%. Mechanically, 2× liquidates at a
33.3% asset decline under 25% maintenance but at 28.6% under 30%, and SPY's
realised max drawdown over this sample is **−33.7%**. One hardcoded digit
decided whether the headline sizing conclusion held.

**Fix:** default raised to **0.30** (realistic CIRO/IBKR-CA), sourced in the
docstring, and the CLI now prints a **sensitivity row across 25/30/35/50%** so
the answer is never a single unqualified number.

### 6. ✅ `cli.py leverage`: table hid liquidation and understated its drawdown
`leverage_scan` computed `realised_liquidated` but no consumer printed it, and
`realised_max_dd` is measured on the post-liquidation **frozen** curve, so a
wiped-out account reports a *shallower* drawdown than it suffered.

Measured: SPY at 3× printed `−30% / −39.0% DD / 51.7% P(call)` with
`realised_liquidated=True`: force-closed, and absent for the +343% that
followed: while QQQ at 3× printed `+1751%` with `realised_liquidated=False`.
Both rendered as ordinary path outcomes.

**Fix:** a `LIQ` column marks liquidated realised paths, and the drawdown of a
liquidated path is reported as −100% of *risk capital at that point* with the
freeze noted, so ruin is never cosmetically shallower than survival.

### 7. ✅ `cli.py greeks --cad`, header printed the USD span over a truncated table
`span0/span1` were bound from the pre-conversion USD basket and never updated,
while `to_cad` drops everything before the first Bank of Canada observation
(503 days).

Measured SPY CAGR: **13.79%** (USD from 2015-01-05), **15.07%** (USD from
2017-01-03), **15.64%** (CAD from 2017-01-03). So the reported "CAD raises CAGR
13.8% → 15.6%" attributed **+1.85pp to currency when +1.28pp was simply the
shorter window** and only ~+0.57pp was FX, consistent with USD/CAD moving just
+4.8% over the period.

**Fix:** the header now prints the *actual* covered span, and the footer reports
the like-for-like USD figure over the same window so the FX contribution is
isolated rather than confounded with truncation.

## Tier 2: `rank/features.py` (the `indicators` command)

This module accounted for 5 of the 15 findings and was **not yet committed**
when reviewed, which is the only reason none of its numbers shipped.

### 8. ✅ IC t-test ignored forward-return overlap → ~27% false-positive rate
Monthly Spearman ICs computed on 63-day forward returns were tested with
`ttest_1samp` as if independent. Adjacent months share ~2/3 of their outcome
window.

Measured over 200 replications on a **pure-null** feature (120 monthly ICs,
h=63): sd of the reported `t` is **1.88** instead of 1.0, and **P(|t|>2) =
27.5%** against a nominal 5%. At h=21 (non-overlapping) the same simulation
gives sd 1.03, P=4.0%, confirming overlap as the cause. End-to-end, with
disclosed and control drawn from the *same zero-alpha process*,
`compare_features` flagged `disclosure_specific=True` on **26.7% of runs**.

`timescale.block_test` existed in this repo to correct exactly this and was not
used. **Fix:** both the single-sample and paired tests now aggregate ICs into
non-overlapping blocks of `ceil(horizon/21)` months before testing.

> Note: this bug inflates false **positives**, so the null result the command
> actually produced was, if anything, conservative. The *method* was unsound
> either way.

### 9. ✅ No sign guard, a control-only feature was flagged as a winner
`disclosure_specific = q_fdr < 0.05` used a two-sided p with no direction check.
Sibling modules guard direction (`exits.py` ANDs `vs_base > 0`; `timescale.py`
ANDs `~underpowered`); this did not.

Reproduced: disclosed with no signal, control with a strong one gives
`ic_diff=−0.867, t_diff=−38.7, q_fdr=2.8e-37, disclosure_specific=True`, and the
CLI printed it **in green** as a discovery. The strongest possible evidence that
a feature is *generic* was reported as the headline positive result.

**Fix:** `& (ic_diff > 0)`, plus a test covering the negative direction.

### 10. ✅ Trade-only features could never be tested, yet were labelled "generic factor"
`build_control` sets all five `TRADE_FEATURES` to NaN, so `p_diff`/`q_fdr` stay
NaN and `NaN < 0.05` is False. Any of them exceeding |t|>2 fell into the CLI's
fallback branch and printed *"predictive, but NOT vs control (generic factor)"*.

Reproduced: a synthetic `lag_days` genuinely driving `fwd` yields
`t_disclosed = −52.70` and that exact label. `lag_days` is **disclosure-only by
definition**, a random stock has no filing lag, so the label asserted the
precise opposite of the truth, and the unconditional verdict ("Whatever predicts
returns here predicts them just as well in random stocks") was stated over 5 of
13 features that were never tested against random stocks.

**Fix:** trade-only features are reported in a separate section labelled
"disclosure-only (no control possible by construction)", the generic-factor
label is only applied where a control exists, and the summary verdict is scoped
to controllable features.

### 11. ✅ Control universe drew forward-filled **dead** tickers
Eligibility was `np.isfinite(pv) & (pv > 0)` on the **ffilled** matrix, so a
ticker that stopped printing in 2016 stayed drawable through 2026 at a frozen
price. `engine.py` deliberately keeps the raw matrix for exactly this reason;
`build_control` threw it away.

Measured (per_date=3, seed 0): **71 of 4,766 control rows** are dead tickers with
`vol_63 == 0.0`, `mom_21 == 0.0`, `dd_from_high == 0.0` exactly and
`fwd = −(benchmark) − cost`; mean forward excess **−5.21%** vs **+0.008%** for
live controls (323 rows have `dd_from_high == 0` exactly). Because the ICs are
Spearman these are not diffuse noise, they are exact ties at the *extreme* rank
of two features with systematically negative outcomes, biasing `ic_control`
precisely where rank correlation has the most leverage.

**Fix:** eligibility now requires a **real print in the un-ffilled matrix**,
matching the engine.

### 12. ✅ `quintile_spread`: `qcut` could collapse to one bucket, and the t measured the wrong thing
Two defects in one function:
- The guard `nunique() < q` does not prevent `qcut(duplicates="drop")` from
  collapsing: `n_filers_30d` is ~97% zeros, so `nunique() >= 5` while all five
  edges are 0. Reproduced → **one** bucket, `spread = 0.0` exactly, and a
  `t = 0.39` built from float residuals ~1e-18, printed under a "by quintile"
  header.
- Pooling top-bucket returns with negated bottom-bucket returns estimates
  `mean_top − mean_bot` only when both are equally represented *within each
  month*. `qcut` equalises counts sample-wide, not per month. Reproduced with
  both buckets drawn from an identical distribution (true spread **exactly 0**,
  sample mean fwd −2.9%): reported spread −0.25% (correct) with **t = −3.61**
  (the level, not the spread), 35 months contributed to the top bucket vs 7 to
  the bottom.

**Fix:** assert the realised bucket count and bail if < q; compute the spread
t-stat from the **per-month paired difference** of bucket means.

### 13. ✅ Control used a scalar mean cost while disclosed used per-trade cost
The docstring claimed "identical forward-return construction". `roundtrip_cost`
is a deterministic function of share price (~26bps at $200, ~226bps at $0.50),
and share price correlates with `mom_252`, `vol_63` and `dd_from_high`, exactly
the features `ic_diff` isolates. A constant shift is rank-invariant for the
control; the varying one is not for the disclosed arm, so the asymmetry landed
entirely in the reported statistic.

**Fix:** control observations are charged the same price-dependent cost model.

### 14. ✅ `forward_excess` re-derived what the engine already returned
`run_event_study` had already computed `(p1/p0−1) − (b1/b0−1) − roundtrip_cost`
at the identical `entry_pos`; `build_disclosed` threw the column away and
recomputed it. Half-compliance with methodology rule 2.1 ("new analyses must consume
`run_event_study`"): it consumed the engine for *positions* and re-implemented
the *measurement*, so the §5b price guard would have to be maintained twice.

**Fix:** the disclosed arm reads `h{horizon}` from `per_trade`. `forward_excess`
survives only for the control arm (which has no trades to run through the
engine) and is documented as such.

## Tier 3: data integrity & infrastructure

### 15. ✅ `scrape/sources.py`: pdfplumber guard missed the scheduler, and burned the resume cursor
The new guard was added only to the `scrape-house` CLI command, but
`HouseClerkSource.run_once` reaches `scrape_recent_ptrs` unguarded and
`scrape_sources` defaults to `["auto"]`. Worse, `house_clerk.py` does
`seen.add(f.doc_id)` **before** `_extract_pdf_text` and persists `seen`
unconditionally.

So on a machine without pdfplumber, `python -m copytrade scrape` reports a clean
run, ingests **zero** House PTRs, and writes every DocID into the resume cursor.
Installing pdfplumber afterwards **recovers nothing**, later runs skip them all;
only `scrape-house --reparse` (which DELETEs every `source='house_clerk'` row)
repairs it. The project log claimed "The CLI now refuses to run without it."

**Fix:** the guard moved into `scrape_recent_ptrs` itself (the single choke
point), and a DocID is only marked seen once its text layer was actually
extracted: so a missing dependency costs a retry, never the data.

### 16. ✅ `market.py`: backoff skipped on the exception it exists for
The `continue` on a batch exception bypassed `time.sleep(pause)`, so no delay
applied in exactly the rate-limit case the retry loop was written to survive:
when yfinance starts throwing at ticker ~600 of 2,000, every remaining chunk is
re-fired instantly and passes 2-3 hit the same wall. 1,268 tickers remained
unpriceable after the real run.

Also: per-chunk provenance was merged only inside `if len(df):`, so
`yfinance_error` was **discarded precisely when a chunk returned nothing**, a
provider outage was then published by `report.py` as "unpriceable/delisted
survivorship caveat".

**Fix:** sleep on the failure path (that is the path that needs it), skip the
trailing sleep after the final chunk of the final pass, and always merge
provenance.

### 17. ✅ `currency.py`: FX forward-filled past its last observation
The docstring forbids back-filling ("would fabricate FX history"), but the
unbounded `ffill` did the same thing forward, undetected. Reproduced by
truncating FX at 2020-01-02: `to_cad` reported full coverage to 2026 while 6.5
years of the curve were multiplied by a frozen 2020 rate, and reported that
frozen rate's move as the realised currency contribution. `fx-refresh` is a
manual command, so a stale table is the *expected* state.

**Fix:** `ffill(limit=...)` bounded to a few trading days (real gaps are
holidays), dates beyond the last observation are dropped and counted, and the
info dict reports `fx_last_observation` so staleness is visible.

### 18. ✅ `costs.py`: docstring said the 1% cap was deliberately NOT modelled
Lines 30-31 read *"Max-1%-of-value commission cap (IBKR) is intentionally NOT
modeled: it only binds on sub-$100 orders"* while line 108 set
`commission_max_pct=0.01` and the neighbouring comment justified it as having
dragged the sample mean to −280%. Both cannot be true.

The stated reason was also false: with `commission_per_share=0.005` the cap binds
whenever `0.005·(notional/p) > 0.01·notional`, i.e. for **any order in a stock
priced under $0.50, at any size**.

The project log §5b blames precisely this class of doc/code divergence for invalidating
the project's earlier numbers, so the next reader had documented grounds to
delete the cap and reintroduce the bug.

## Checked and clean: do not re-investigate

Verified by execution, no defect:

- **`benjamini_hochberg`** matches `statsmodels.multipletests(method="fdr_bh")`
  exactly on 5 random 40-test grids.
- **`levered_paths_vec` vs `levered_path`**, 0 mismatches over 2,160 paths
  (both rebalance modes × 6 leverage levels × 3 vol regimes, 174 liquidations
  exercised). No off-by-one in `frozen_at` / `take_along_axis`.
- **`np.fmax.accumulate(np.nan_to_num(seg, nan=-np.inf))`** in `apply_exit` is
  correct: `nan_to_num` computes masks before assignment, so `neginf` does not
  clobber `nan=-inf`.
- **`argmax` on all-False** in `levered_paths_vec` is fully guarded by
  `any_breach`.
- **`_block_bootstrap` is hoisted** above the leverage loop, not recomputed per
  level.
- **Vectorising `price_features` would be slower**, measured 0.46s for 15,583
  rows via slicing vs ~7s for a per-ticker rolling precompute across 2,299
  tickers (only ~6.8 trades/ticker). Do not "optimise" this.
- **`config.toml` / `Settings` / CLI option defaults** match field-for-field.
- **`pdfplumber` is imported lazily**, so the requirements pin does not break the
  no-pdfplumber import path.
- Correct real-world constants: IBKR $0.005/share, $1 min, 1% cap; 252 trading
  days; 21/month; Wealthsimple 1.5% FX; CANADA.md 2026 TFSA figures ($7,000 new
  / $109,000 cumulative).

is reliably negative by the round-trip cost; the persistence null; and the
"no exit rule beats the baseline" conclusion (`vs_base` truncated both legs
identically).
